## 1. Цель работы

Настроить CI-пайплайн со статическим анализом кода (SAST), анализом
зависимостей (SCA) и выгрузкой отчётов; организовать работу с секретами
приложения через внешнее хранилище и продемонстрировать децентрализованный
и централизованный подходы к их провижинингу.

## 2. Репозиторий и структура

Репозиторий: `<📌 ССЫЛКА НА GITHUB/GITLAB>`


## 3. Выбранные инструменты

| Тип | Инструмент | Обоснование |
|---|---|---|
| SAST #1 | **Bandit** | AST-анализ Python-кода, простая интеграция, встроенные проверки (B3xx, B6xx) |
| SAST #2 | **Semgrep** | мультиязычные rulesets (`p/python`, `p/secrets`), легко добавлять свои правила |
| SCA | **pip-audit** | проверяет requirements.txt и транзитивные зависимости по базе PyPI/OSV |
| Бонус | **Gitleaks** | сканирует историю git на утёкшие секреты |

## 4. CI-пайплайн

Стадии: `build` (установка зависимостей, байт-компиляция, импорт-проверка) →
`sast` (bandit_sast, semgrep_sast) → `sca` (pip_audit_sca) → `secrets`
(gitleaks_secrets). Каждый анализ выгружает отчёты как артефакты с
`when: always` — отчёты есть даже при ненулевом exit code.

### Разбор находок

**Bandit** (намеренно оставленный legacy-модуль `app/legacy_report.py`):
- B324 — md5 для паролей (HIGH) → фикс: bcrypt/argon2;
- B311 — `random` для токенов → фикс: `secrets.token_hex()`;
- B602/B605 — shell-инъекция в `subprocess.run(..., shell=True)` → фикс:
  список аргументов без `shell=True`.

**pip-audit**: `requests==2.28.0` (CVE-2023-32681, CVE-2024-35195 и др.),
`urllib3 1.26.20`, `flask 3.1.0` — продемонстрировано обнаружение и
remediation: поднять версии (`requests>=2.32`, `flask>=3.1.3`).

**Gitleaks**: 0 находок — секреты не в git (`.env` и `.vault-approle.env`
в `.gitignore`).

## 6. Секреты приложения

Перечень и правила: `docs/SECRETS.md`. Ключевые секреты: `APP_SECRET_KEY`,
`JWT_SECRET`, `DATABASE_URL` (содержит пароль БД), `EXTERNAL_API_TOKEN`,
`SMTP_*`; в централизованном режиме — только bootstrap `VAULT_*`.

Приложение читает секреты **только** через `app/config.py`
(`APP_SECRETS_SOURCE=env|file|vault`), из исходников секретов нет,
эндпоинты отдают только имена/флаги, при нехватке — fail-fast с перечнем
имён (без значений).

📌 СКРИНШОТ: вывод `curl /config-status` (только имена секретов)

## 7. Децентрализованный провижининг

Каждое окружение само генерирует и хранит свои секреты (файл/env), без
центрального хранилища. Ротация = перезапуск скрипта.

```bash
./scripts/provision_decentralized.sh   # генерирует .env (chmod 600)
make run                               # приложение читает .env
```

📌 СКРИНШОТ: вывод скрипта + `ls -l .env` (права 600)
📌 СКРИНШОТ: `curl /health` → `"secrets_source":"file"` и `/admin/ping` 200/401

## 8. Централизованный провижининг (HashiCorp Vault)

Единое хранилище секретов; приложение аутентифицируется scoped-идентичностью
AppRole `lab10-app` с least-privilege политикой (`vault/policy.hcl`, только
чтение `secret/lab10`), root-токен приложению не выдаётся. Секреты
фETCH-атся приложением на старте (`app/config.py`, hvac) и не лежат на диске.

```bash
./scripts/provision_centralized.sh     # Vault dev + секреты + AppRole
make run-vault                         # приложение получает секреты из Vault
```

📌 СКРИНШОТ: вывод provision_centralized.sh
📌 СКРИНШОТ: `curl /health` → `"secrets_source":"vault"` и `/admin/ping` 200
с токеном, полученным из Vault (`VAULT_TOKEN=lab10-root vault kv get
-field=EXTERNAL_API_TOKEN secret/lab10`)

## 9. Выводы

- CI автоматически при каждом push проверяет код (2 SAST) и зависимости
  (1 SCA), отчёты сохраняются как артефакты — воспроизводимо и без локальных
  инструментов.
- Секреты полностью вынесены из кода во внешнее хранилище; продемонстрированы
  оба подхода: файл/env на стороне окружения (просто, но ротация вручную) и
  централизованный Vault с AppRole-идентичностью и least-privilege политикой
  (ротация и аудит в одном месте).
- Инструменты нашли реальные проблемы (weak hash, shell injection, устаревшие
  зависимости) — показан цикл: обнаружение → разбор → remediation.
